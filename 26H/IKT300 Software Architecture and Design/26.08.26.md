**Every system has a software architecture**
 - Every system comprises elements and relations among them to support some type of reasoning.
 - The architecture may not be known to anyone.
	 - Perhaps the designers are gone
	 - No documentation
	 - Source code lost
 - Architecture can exist independently of its description or specification.
 - Documentation is critical.
#### Architecture includes behaviour
- The bahviour of eaech element is part of the architecture insofar as that behaviour can be used to reason about the system.
- Includes how elements interact with each other, which is clearly part of definition of architecture.

	- names of boxes correlates to functionality and behaviour,

### Structures and Views
- A *view* is a representation of a coherent set of architectural elements, as written by and read by system stakeholders.
	- A view consists of a reprerensteation of a set of elements and the relations among them.
- A *structure* is the set of elements itself, as they exist in software or hardware.
- In short a view is a representation of a structure.
	- For instance, a module structure is the set of the systems modules and their organization.

#### Types of structures/views

##### Module
- Module structures elements are some kind of classes or layers, or merely divisions of functionality, all of which are units of implementation.
- Modules are assigned responsibility, less emphasis in these structures on how the software manifests at runtime.
- They answer the following questions:
	- What is the primary functional responsibility assigned to each module?
	- What other software elements is a module allowed to use?
	- What other software does it actually use and depend on?
	- What modules are related to other modules by generalization or specialization (i.e., inheritence) relationships. 

##### Component and connector
- Component-and-connector structures embody decision as to how the system is to be structured as a set of elements that have runtime behaviour (components) and interactions (connectors).
- Elements are runtime components such as services, peers, clients, servers, filters, or many othe rytpes of runtime element.
- Connectors are the communication vehicles among components, such as call-return, process syncrhonization operators, pipes, or others.
- Component-and-connector views answer these questions:
	- What are the major executing components and how do they interact at runtime?
	- What are major shared data stores?
	- Which parts of the system are replicated?
	- How does data progress through the system?
	- What parts of the system can run in parallel?
	- Can the system's structure change as it executes and, if so, how?
- Component-connector views are crucially important for asking questions about the systems runtime properties such as performance secruity avaialbleilityte and more.
